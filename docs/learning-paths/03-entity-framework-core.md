# 03. Data Access with Entity Framework Core — Book Catalog API

> Part of the [.NET API Development Roadmap](../dotnet-api-roadmap.md). Continues the Book Catalog
> API from [Path 01](01-aspnet-core-fundamentals.md) and
> [Path 02](02-dependency-injection-configuration.md). Build-it project — contracts, test requests,
> and checklists only. No C# solution code.

## Project Brief

Up to now, "the database" has been a `List<Book>` sitting in memory, gone the moment the process
restarts. This path replaces it with a **real, persistent database** using Entity Framework Core,
and — just as importantly — introduces the first real **relationship** in your domain: a book has
exactly one author, and an author can have many books.

This is also where you'll deliberately run into two classic EF Core problems on purpose — a
circular-reference serialization failure, and an N+1 query — so you recognize them instantly the
next time they show up somewhere that isn't a learning project.

## Prerequisites

- [ ] [Path 01](01-aspnet-core-fundamentals.md) and
      [Path 02](02-dependency-injection-configuration.md) are both fully done — their Definitions
      of Done pass, and the book store is already resolved through an interface (`IBookStore` or
      your equivalent name).
- [ ] You've picked one database engine to actually use for this path. SQLite is recommended — it's
      a single file, needs no server install, and is enough to learn every EF Core concept here.
      SQL Server LocalDB is a fine alternative if you'd rather use that. Don't spend time
      supporting both; pick one.

## Rules

- No repository/unit-of-work abstraction layer yet — that's Path 04. Keep talking to EF Core
  through the same kind of store interface you already established in Path 02.
- No DTOs and no mapping library yet — that's Path 05. You're still returning entities directly,
  which is exactly what makes the circular-reference problem in M5 real instead of theoretical.
- No FluentValidation — keep doing required-field/range checks by hand, same as before.
- Don't try to support two different database providers "just in case." Pick one for the core
  milestones; swapping providers is a stretch goal, not a requirement.
- Every milestone must still be manually tested with real HTTP requests before you check it off.

## Data Contract

### `Author`

| Field | Type | Required | Rule |
|---|---|---|---|
| `id` | integer | server-assigned | Generated by the database. |
| `name` | string | yes | Non-empty after trimming; reasonable max length (e.g. 150 chars). |

### `Book` (updated from Path 01/02)

The plain `author` string field is gone. In its place:

| Field | Type | Required | Rule |
|---|---|---|---|
| `id` | integer | server-assigned | Generated by the database. |
| `title` | string | yes | Same rule as Path 01. |
| `publishedYear` | integer | yes | Same rule as Path 01 (`1450`..current year). |
| `genre` | string | yes | Same rule as Path 01. |
| `authorId` | integer | yes | Must reference an existing `Author`. This is the field the client writes. |

### Book response shape (read-only convenience projection)

When you **return** a book, include a minimal nested `author` object alongside `authorId`, loaded
through the relationship rather than looked up separately:

```json
{
  "id": 4,
  "title": "Dune",
  "publishedYear": 1965,
  "genre": "Science Fiction",
  "authorId": 2,
  "author": {
    "id": 2,
    "name": "Frank Herbert"
  }
}
```

`author` here is a read convenience, not a second writable field — `authorId` is still what a
client sends on create/replace.

## Suggested Project Structure

Additions on top of what Paths 01–02 already gave you:

- [ ] An `Author` entity class alongside your existing `Book` class, with `Book` updated to carry
      `AuthorId` and an `Author` navigation property, and `Author` carrying a `Books` navigation
      collection.
- [ ] A `DbContext` exposing both entities.
- [ ] An `IAuthorStore`-style interface (mirroring your existing `IBookStore`), plus an
      EF-Core-backed implementation.
- [ ] Your existing `IBookStore` interface stays the same shape from the outside; only its
      implementation changes to use the `DbContext` instead of an in-memory list.
- [ ] A `Migrations` folder (generated for you once you start adding migrations — don't hand-edit
      it).

## Milestones

Work top to bottom. Each one should run and be manually testable before you start the next.

### M1 — Model the Relationship

- [ ] Update `Book`: remove the plain `Author` string field; add an `AuthorId` foreign key and an
      `Author` navigation property.
- [ ] Add the new `Author` entity with a `Books` navigation collection.
- [ ] This milestone is just the shape of your domain classes — don't wire up persistence yet.

**Things to decide and be consistent about:**

| Question | Why it matters |
|---|---|
| Is `Book.Author` nullable? | It shouldn't be — `AuthorId` is required, so every book has exactly one author. |
| Does `Author.Books` start as an empty collection or `null` by default? | Decide once, so nothing downstream has to null-check inconsistently. |

### M2 — Wire Up EF Core

- [ ] Install the EF Core provider package for the database engine you picked (SQLite or SQL
      Server), plus the EF Core design/tooling package needed for migrations.
- [ ] Add a connection string under its own configuration section — you already know exactly how
      to read configuration values from Path 02, this is just another one.
- [ ] Create a `DbContext` exposing `DbSet<Book>` and `DbSet<Author>`, and register it in DI.
      Look up what lifetime EF Core's registration helper uses by default, and be ready to explain
      *why* that lifetime is correct for something that wraps a single unit of work.
- [ ] Configure the relationship and the field rules from the [Data Contract](#data-contract)
      (required fields, max lengths, the foreign key) using either fluent configuration or data
      annotations — your choice, but be consistent.

### M3 — First Migration

- [ ] Generate your first migration and actually **open and read** the generated files before
      applying anything — you should be able to explain what each part does, not just trust it
      blindly.
- [ ] Apply the migration to create the real database schema.
- [ ] Decide, deliberately, whether pending migrations should be applied automatically at startup
      — and if so, gate that behind `IWebHostEnvironment.IsDevelopment()` the same way you gated
      the diagnostics endpoint in Path 02 — or applied manually via the CLI as a separate step.
      Document which you picked and why.

**Edge case to verify:** if you chose the manual route, start the app with a pending, unapplied
migration and confirm the failure you get is something you could actually diagnose, not a cryptic
crash.

### M4 — Swap the Store's Internals to EF Core

- [ ] Replace the in-memory implementation behind `IBookStore` with one backed by your
      `DbContext`, **without changing the interface's public shape**. This is the entire point of
      coding to an interface back in Path 02 — prove it by not touching a single endpoint handler.
- [ ] Update the create/replace endpoints for the new `AuthorId` field in place of the old `author`
      string (this is the one place the contract itself actually changed).
- [ ] Re-run every applicable Path 01/02 scenario (adjusted for `authorId`) and confirm identical
      externally observable behavior for everything that didn't intentionally change.

**New, genuinely different behavior to verify:** restart the app and confirm your books are
**still there** — persistence across restarts is the whole reason this path exists, and it's the
first milestone where you can actually observe it.

### M5 — Expose Author Data on Book Responses (and Solve the Cycle)

- [ ] When returning a book (list or single), include its author's `id` and `name`, loaded through
      the relationship — not via a second manual lookup.
- [ ] You will very likely hit a **circular reference** the first time you try to serialize an
      entity whose navigation properties point both ways (`Book` → `Author` → `Books` → `Author`
      → …). Reproduce this failure **on purpose** first, so you recognize the error the next time
      it happens somewhere that isn't a learning project.
- [ ] Then apply **one** clean fix and be ready to explain the trade-off you accepted:

| Option | How it works | Trade-off |
|---|---|---|
| Configure the JSON serializer's cycle handling app-wide | The serializer silently stops whichever reference would create a cycle | Quick and global, but can quietly mask the same problem showing up somewhere you didn't expect |
| Exclude the back-navigation (`Author.Books`) from serialization directly on that property | Only that one reverse-navigation is ever skipped | Precise and intentional, but every new bidirectional relationship later needs the same treatment by hand |
| Never load the back-navigation in a query whose result gets serialized | No cycle exists because the data was never fetched in the first place | The most correct long-term instinct — and exactly what Path 05's DTOs make automatic |

### M6 — Minimal Author Endpoints

- [ ] `POST /api/authors` → `201 Created` + `Location` header; `400` if `name` is missing/blank.
- [ ] `GET /api/authors` → `200` + all authors.
- [ ] `GET /api/authors/{id}` → `200` + author, or `404` if it doesn't exist.

**Edge cases to verify:**

| Scenario | Expected result |
|---|---|
| Create an author with a valid name | `201` + `Location` pointing at the new author. |
| Create an author with a blank/whitespace-only name | `400`. |
| Get an author that doesn't exist | `404`. |

### M7 — Validate `AuthorId` on Book Create/Replace

- [ ] Before saving a book on `POST` or `PUT`, confirm the referenced `AuthorId` actually exists.
- [ ] If it doesn't, this is a **validation failure of the request body**, not a "resource looked
      up by the URL doesn't exist" situation — return `400 Bad Request`, the same family of error
      as a missing `title`, not `404`.

**Edge cases to verify:**

| Scenario | Expected result |
|---|---|
| `authorId` referencing an existing author | Success, book created/replaced with that author. |
| `authorId` referencing a nonexistent author (e.g. `9999`) | `400`. |
| `authorId` missing from the body entirely | `400`. |
| `authorId` is `0` or negative | `400`. |

### M8 — Tracking vs. No-Tracking Pass

- [ ] Audit every **read-only** query (list books, get book by id, list authors, get author by id)
      and make sure each one explicitly opts out of change tracking, since none of them need to
      write anything back.
- [ ] Audit every **write** path (create, replace) and confirm those still track normally — EF Core
      needs tracking there to detect what to insert/update.
- [ ] Pick one query in your own code and write down, specifically, what would be wasted
      (memory/CPU tracking entities that are only ever read) if you left tracking enabled there.

### M9 — Find and Fix an N+1

- [ ] Add a `bookCount` to each author in `GET /api/authors`'s response.
- [ ] Implement it the **naive way on purpose first**: fetch all authors, then separately query
      each author's book count in a loop.
- [ ] Turn on EF Core's SQL command logging (look up how) and count the actual queries fired for,
      say, 5 authors — you should see the classic N+1 shape: one query for the authors, plus one
      more *per author*.
- [ ] Fix it to run as a single query (e.g. a grouped/joined query), re-run with logging still on,
      and confirm the query count actually dropped — not just that the JSON response looks the
      same.

### M10 — Full Regression Pass + Migration Hygiene

- [ ] Full regression across every Path 01/02/03 scenario (updated for the `Author` relationship).
- [ ] Confirm a completely fresh checkout of the project (no local database file) can go from zero
      to a working, migrated database using only the steps you've documented for yourself.
- [ ] Confirm your migration **files** are committed to source control, while the actual database
      data file is not (add it to `.gitignore` if you're using SQLite).

## Manual Test Script

Run in order, against a freshly created (migrated, empty) database.

```http
@baseUrl = https://localhost:5001

### 1. Create author 1 -> 201 + Location
POST {{baseUrl}}/api/authors
Content-Type: application/json

{ "name": "Frank Herbert" }

### 2. Create author 2 -> 201 + Location
POST {{baseUrl}}/api/authors
Content-Type: application/json

{ "name": "J.R.R. Tolkien" }

### 3. Create author with blank name -> 400
POST {{baseUrl}}/api/authors
Content-Type: application/json

{ "name": "   " }

### 4. List authors -> 200 + the 2 created authors
GET {{baseUrl}}/api/authors

### 5. Create a book referencing author 1 -> 201, response includes nested author
POST {{baseUrl}}/api/books
Content-Type: application/json

{
  "title": "Dune",
  "publishedYear": 1965,
  "genre": "Science Fiction",
  "authorId": 1
}

### 6. Create a book referencing a nonexistent author -> 400
POST {{baseUrl}}/api/books
Content-Type: application/json

{
  "title": "Ghostwritten",
  "publishedYear": 2000,
  "genre": "Mystery",
  "authorId": 9999
}

### 7. List books -> nested author data present, no serialization error
GET {{baseUrl}}/api/books

### 8. Get authors with bookCount -> counts match what you actually created
GET {{baseUrl}}/api/authors

### 9. Replace book 1 with a different, valid authorId -> success
PUT {{baseUrl}}/api/books/1
Content-Type: application/json

{
  "title": "Dune",
  "publishedYear": 1965,
  "genre": "Science Fiction",
  "authorId": 2
}

### 10. Confirm the author changed on the book
GET {{baseUrl}}/api/books/1

### 11. Replace a book with a nonexistent authorId -> 400
PUT {{baseUrl}}/api/books/1
Content-Type: application/json

{
  "title": "Dune",
  "publishedYear": 1965,
  "genre": "Science Fiction",
  "authorId": 9999
}

### 12. Delete the book -> 204
DELETE {{baseUrl}}/api/books/1

### 13. Confirm deletion -> 404
GET {{baseUrl}}/api/books/1
```

Manual (non-HTTP) step: after running the script once, **stop and restart the app**, then repeat
request #7 (`GET /api/books`) — the surviving book(s) must still be there. This is the concrete
proof that persistence actually works now, not just that the code compiles.

## Stretch Goals

Only after every milestone above is checked off:

- [ ] Add `DELETE /api/authors/{id}`, but make it return `409 Conflict` if that author still has
      books — don't silently cascade-delete a person's entire bibliography as a side effect.
- [ ] Add an `?authorId=` filter to `GET /api/books`, mirroring the `?genre=` filter from Path 01.
- [ ] Add a second migration for a small schema change (e.g. an optional `Description` field on
      `Book`) so you practice the *incremental* migration workflow, not just the very first one.
- [ ] Switch your project from your original provider to the other one (SQLite ↔ SQL Server
      LocalDB) and confirm your store implementation barely has to change — proving the
      abstraction EF Core itself provides over the underlying database engine.
- [ ] Enable lazy-loading proxies, deliberately trigger a hidden N+1 through lazy loading without
      explicitly calling `Include` anywhere, observe it in the SQL log, and then decide for
      yourself whether you actually want lazy loading turned on for this project. (Most real teams
      turn it off for exactly the reason you just saw.)

## Definition of Done

- [ ] M1–M10 all checked off, in order, each with manual test evidence.
- [ ] Books and authors persist across an app restart.
- [ ] Every book response includes correct nested author data with no serialization crash.
- [ ] `AuthorId` is validated on both create and replace, returning `400` for a nonexistent
      reference.
- [ ] All read-only queries are confirmed no-tracking; all write paths are confirmed still
      tracked.
- [ ] The `GET /api/authors` book-count N+1 was reproduced, observed via SQL logging, and then
      actually fixed to a single query.
- [ ] Migration files are committed; the local database data file is not.
- [ ] The full Path 01/02 regression pass still succeeds (adjusted for `authorId`).

## Self-Review Checklist

- [ ] You can explain, specifically for this app, why the DbContext is registered at the lifetime
      it is — not just "because that's the default."
- [ ] You can reproduce the circular-reference error on demand and explain, in your own words, why
      it happens.
- [ ] You can point at the SQL log output that proves the N+1 existed, and the SQL log output that
      proves your fix reduced it to one query.
- [ ] Nothing in your endpoint handlers changed when you swapped the store's implementation in M4
      — if something did, the interface boundary wasn't clean.
- [ ] You know, off the top of your head, which of your queries are no-tracking and why each one
      is.
